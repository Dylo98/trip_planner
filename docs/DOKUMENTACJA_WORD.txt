1.1. PRZEGLĄD STOSU TECHNOLOGICZNEGO

TripPlanner to aplikacja mobilna zbudowana w oparciu o nowoczesny stos technologiczny, łączący Flutter jako framework UI z Firebase jako kompleksowym rozwiązaniem backendowym.

1.2. FRAMEWORK I JĘZYK

• Flutter SDK >= 3.6.0 - Cross-platformowy framework UI od Google
• Dart >= 3.6.0 < 4.0.0 - Język programowania zoptymalizowany pod UI

Dlaczego Flutter?
• Jeden codebase - aplikacja działa na Android, iOS, Web, Windows, macOS, Linux
• Hot Reload - natychmiastowe odświeżanie zmian podczas developmentu
• Wydajność - kompilacja do natywnego kodu maszynowego
• Bogaty ekosystem - tysiące gotowych pakietów na pub.dev

1.3. BACKEND - FIREBASE

Firebase Core 3.13.0 - Inicjalizacja Firebase
Firebase Auth 5.5.2 - Autoryzacja użytkowników
Cloud Firestore 5.6.7 - Baza danych NoSQL w czasie rzeczywistym
Firebase Storage 12.4.6 - Przechowywanie plików (zdjęcia)

Firebase Authentication - obsługiwane metody logowania:
• Email + hasło
• Reset hasła przez email

Cloud Firestore:
• Baza danych dokumentowa NoSQL
• Synchronizacja w czasie rzeczywistym
• Offline persistence
• Skalowalna bez konfiguracji serwera

Firebase Storage:
• Przechowywanie zdjęć podróży
• Zdjęcia profilowe użytkowników
• Zdjęcia markerów na mapie

3.1. KONFIGURACJA FIREBASE

Krok 1: Utwórz projekt Firebase
1. Przejdź do https://console.firebase.google.com/
2. Kliknij "Add project"
3. Podaj nazwę projektu (np. "trip-planner")
4. Opcjonalnie włącz Google Analytics
5. Kliknij "Create project"

Krok 2: Włącz wymagane usługi

Authentication:
1. Build > Authentication
2. Get started
3. Sign-in method > włącz Email/Password

Cloud Firestore:
1. Build > Firestore Database
2. Create database
3. Wybierz tryb (Production/Test)
4. Wybierz lokalizację (np. europe-west1)

Firebase Storage:
1. Build > Storage
2. Get started
3. Wybierz tryb i lokalizację

Krok 3: Zainstaluj FlutterFire CLI
dart pub global activate flutterfire_cli

Krok 4: Skonfiguruj Firebase
firebase login
flutterfire configure

3.2. KONFIGURACJA GOOGLE MAPS API

Krok 1: Włącz API w Google Cloud Console
1. Przejdź do https://console.cloud.google.com/
2. APIs & Services > Library
3. Włącz:
   • Maps SDK for Android
   • Maps SDK for iOS
   • Maps JavaScript API
   • Places API
   • Geocoding API

Krok 2: Utwórz klucz API
1. APIs & Services > Credentials
2. Create Credentials > API key

Krok 3: Skonfiguruj w projekcie

Android (android/app/src/main/AndroidManifest.xml):
<meta-data
    android:name="com.google.android.geo.API_KEY"
    android:value="YOUR_API_KEY"/>

iOS (ios/Runner/AppDelegate.swift):
GMSServices.provideAPIKey("YOUR_API_KEY")

3.3. PLIK .ENV

Utwórz plik .env w głównym katalogu projektu:

GOOGLE_MAPS_API_KEY=your_google_maps_api_key
GOOGLE_AI_API_KEY=your_google_ai_api_key

WAŻNE: Dodaj .env do .gitignore - nigdy nie commituj kluczy API!

3.4. REGUŁY BEZPIECZEŃSTWA FIRESTORE

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;

      match /trips/{tripId} {
        allow read, write: if request.auth != null && request.auth.uid == userId;
      }

      match /shared_trips/{tripId} {
        allow read: if request.auth != null && request.auth.uid == userId;
        allow write: if request.auth != null;
      }
    }
  }
}

4. ARCHITEKTURA
================================================================================

4.1. ARCHITEKTURA FEATURE-FIRST

Projekt wykorzystuje architekturę Feature-First (Modular Architecture) z podziałem na moduły funkcjonalne.

Zamiast tradycyjnego podziału według typu (wszystkie modele w jednym folderze), kod jest organizowany według funkcjonalności biznesowych.

Struktura:
lib/
├── core/                    (Współdzielone zasoby)
│   ├── navigation/
│   ├── theme/
│   ├── utils/
│   └── widgets/
│
└── features/               (Moduły funkcjonalne)
    ├── auth/
    ├── trip/
    ├── budget/
    └── ...

Zalety:
• Modularność - każdy feature jest samodzielną jednostką
• Skalowalność - łatwe dodawanie nowych funkcjonalności
• Czytelność - kod powiązany logicznie jest w jednym miejscu
• Niezależność - zespoły mogą pracować równolegle
• Testowalność - każdy moduł można testować izolowanie

4.2. WZORCE PROJEKTOWE

Facade Pattern:
TripService jako główna fasada delegująca operacje do wyspecjalizowanych serwisów:
• TripCrudService - podstawowe operacje CRUD
• TripImageService - zarządzanie zdjęciami
• TripDeletionService - usuwanie podróży
• MarkerCrudService - operacje na markerach
• MarkerUpdateService - aktualizacja markerów
• MarkerImageService - zdjęcia markerów

Repository Pattern:
Warstwa abstrakcji między logiką biznesową a źródłem danych. Umożliwia łatwą zamianę źródła danych (Firebase → REST API → lokalna baza).

Provider Pattern (Riverpod):
Globalne repozytorium zależności dostępne z dowolnego miejsca w aplikacji.

4.3. WARSTWY APLIKACJI

1. Presentation Layer - Screens, Widgets, Dialogs
2. State Management - Riverpod Providers
3. Business Logic Layer - Services, Repositories, Utils
4. Data Layer - Models, DTOs, Mappers
5. External Services - Firebase, Google Maps, Google AI

4.4. ZASADY SOLID

Single Responsibility - każdy serwis ma jedną odpowiedzialność
Open/Closed - nowe features bez modyfikacji istniejących
Liskov Substitution - modele używają copyWith
Interface Segregation - Facade eksponuje tylko potrzebne metody
Dependency Inversion - serwisy przyjmują zależności przez konstruktor

6.1. AUTORYZACJA (AUTH)

Rejestracja:
• Imię (minimum 2 znaki)
• Adres email (walidowany format)
• Hasło (minimum 6 znaków)

Przepływ rejestracji:
1. Użytkownik wypełnia formularz
2. Walidacja po stronie klienta
3. Utworzenie konta w Firebase Auth
4. Utworzenie dokumentu użytkownika w Firestore
5. Automatyczne zalogowanie
6. Przekierowanie do ekranu głównego

Logowanie:
• Email i hasło
• Automatyczne przekierowanie zalogowanych
• Sesja utrzymywana przez Firebase Auth

Resetowanie hasła:
• Wysłanie emaila z linkiem do resetu

Wylogowanie:
• Czyszczenie sesji
• Przekierowanie do ekranu autoryzacji

Obsługa błędów:
• invalid-email: Nieprawidłowy format email
• user-not-found: Nie znaleziono użytkownika
• wrong-password: Nieprawidłowe hasło
• email-already-in-use: Email zajęty
• weak-password: Hasło za słabe
• too-many-requests: Zbyt wiele prób

6.2. ZARZĄDZANIE PODRÓŻAMI (TRIP)

Tworzenie podróży:
• Nazwa podróży (wymagana)
• Data rozpoczęcia
• Data zakończenia (opcjonalna)
• Zdjęcie główne (opcjonalne)

Typy podróży:
• planned - zaplanowana z datą końcową
• ongoing - spontaniczna bez daty końcowej

Statusy podróży:
• upcoming - nadchodząca (data start > teraz)
• ongoing - w trakcie (start <= teraz <= end)
• completed - zakończona (end < teraz)

Lista podróży:
• Wyświetlanie wszystkich podróży
• Sortowanie po dacie
• Filtrowanie po statusie
• Wizualne rozróżnienie statusów

Szczegóły podróży (dwie zakładki):
1. Szczegóły:
   • Zdjęcie nagłówkowe
   • Nazwa i daty
   • Status podróży
   • Galeria zdjęć
   • Lista markerów

2. Mapa:
   • Widok Google Maps
   • Markery punktów
   • Linie łączące punkty
   • Dodawanie nowych punktów

Edycja:
• Zmiana nazwy
• Zmiana dat
• Zmiana zdjęcia
• Dodawanie/usuwanie markerów

Usuwanie:
1. Potwierdzenie przez dialog
2. Usunięcie zdjęć z Storage
3. Usunięcie dokumentu z Firestore

8.1. TRIPSERVICE (FACADE)

API - Markery:
• addMarkerToTrip(String tripId, MarkerPoint marker)
• deleteMarkerFromTrip(String tripId, String markerId)
• updateMarkerTransportMode(tripId, markerId, transportMode)
• updateMarkerDescription(tripId, markerId, description)
• updateMarkerName(tripId, markerId, name)

API - Zdjęcia markerów:
• addImageToMarker(tripId, markerId, File image)

API - Wydatki:
• updateMarkerExpenses(tripId, markerId, expenses)

9.1. RIVERPOD - PRZEGLĄD

void main() {

    return Text(value);
  }
}

9.2. TYPY PROVIDERÓW

Provider (podstawowy):
Dla obiektów które nie zmieniają się (serwisy, konfiguracja).

final tripServiceProvider = Provider<TripService>((ref) {
  return TripService(...);
});

StateProvider:
Dla prostych stanów (liczniki, flagi, wybory).

final selectedSortingProvider = StateProvider<TripSorting>((ref) {
  return TripSorting.byDateDesc;
});

FutureProvider:
Dla asynchronicznych danych jednorazowych.

final getTripProvider = FutureProvider.family<Trip?, String>((ref, tripId) async {
  final tripService = ref.watch(tripServiceProvider);
  return tripService.getTrip(tripId);
});

StreamProvider:
Dla danych w czasie rzeczywistym (Firestore streams).

final allTripsProvider = StreamProvider<List<Trip>>((ref) {
  final tripService = ref.watch(tripServiceProvider);
  return tripService.getTrips(userId);
});

StateNotifierProvider:
Dla złożonej logiki stanu z wieloma akcjami.

final tripFormProvider = StateNotifierProvider<TripFormNotifier, TripFormState>((ref) {
  return TripFormNotifier();
});

9.3. PROVIDERY W TRIPPLANNER

Trip Providers:
• tripServiceProvider - serwis podróży
• allTripsProvider - wszystkie podróże (stream)
• getTripProvider - pojedyncza podróż (future)
• watchTripProvider - obserwowanie podróży (stream)

Form Provider:
• tripFormProvider - stan formularza nowej podróży

Markers Provider:
• tripMarkersProvider - stan markerów na mapie

9.4. UŻYCIE REF

ref.watch - nasłuchuje zmian, przebudowuje widget:
final trips = ref.watch(allTripsProvider);

ref.read - jednorazowy odczyt (dla event handlerów):
ref.read(tripFormProvider.notifier).submit();

ref.listen - nasłuchuje i wykonuje side effects:
ref.listen<TripFormState>(tripFormProvider, (previous, next) {
  if (next.error != null) {
    // Pokaż snackbar
  }
});

9.5. ASYNCVALUE HANDLING

final tripsAsync = ref.watch(allTripsProvider);

return tripsAsync.when(
  data: (trips) => TripList(trips: trips),
  loading: () => CircularProgressIndicator(),
  error: (error, stack) => Text('Error: $error'),
);

9.6. FAMILY MODIFIERS

Providery parametryzowane:

final watchTripProvider = StreamProvider.family<Trip, String>((ref, tripId) {
  return tripService.watchTrip(tripId);
});

// Użycie:
final tripAsync = ref.watch(watchTripProvider(tripId));
